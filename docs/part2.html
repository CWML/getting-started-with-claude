Analyzing research data with Claude Code

A 90-minute hands-on class for researchers who can read a little R

WarningWork in progress

This class material isn’t complete yet. Expect changes before the class is offered.

In this class you’ll analyze real CDC survey data (NHANES, August 2021–August 2023) with Claude Code in Positron. Claude Code is an AI coding agent: it reads your files, writes code, runs it, and fixes its own errors. You’ll work in its extension panel. You’ll plan first, let Claude build the scripts, and check every step yourself. By the end, you’ll try to reproduce a published CDC estimate of how many U.S. adults have high blood pressure. This page has every prompt, ready to copy.

The goal: this class doesn’t replace learning R or statistics. You’ll learn where a coding agent speeds up good analysis, and where your expertise must stay in control. Each step below says what Claude does and what you decide.

For: researchers, research coordinators, analysts, and clinicians who can read a little R. Getting started with Claude (the Claude app class) helps but isn’t required. If you work in Python, pair with an R user or follow along.

By the end of class, you’ll be able to:

  1. Configure a Claude Code project that protects raw and restricted data.
  2. Implement a plan-first workflow to clean and analyze study data.
  3. Distinguish tasks to delegate to Claude from decisions you keep.
  4. Evaluate AI-generated code and results against the analysis plan.

Before class

ImportantSetup (about 30 minutes)

Do the setup steps before class. In short: a Yale Claude account whose seat includes Claude Code, Positron with the Claude Code extension, R with the class packages (including haven and survey), and git with your name and email set.

Download

nhanes-bp.zip is the class project. It holds:

  • three unmodified CDC data files in data/raw/ (DEMO_L.xpt demographics, BPXO_L.xpt blood pressure readings, BPQ_L.xpt blood pressure questions), with CDC’s codebooks in docs/codebooks/
  • a data dictionary of the variables we use (data/data_dictionary.csv)
  • a one-page analysis plan (docs/analysis-plan.md)
  • CLAUDE.md, the project rules for Claude
  • a fictional stand-in in data/restricted/
  • an excerpt of CDC’s own SAS code in legacy/, for a try-at-home exercise

The R/, output/, and reports/ folders are empty. You’ll fill them in class.

Unzip it somewhere easy to find, such as Documents/. On Windows, right-click the zip and choose Extract All. If you get an nhanes-bp folder inside another nhanes-bp folder, open the inner one. CLAUDE.md should be at the top of Positron’s Explorer. Then open the nhanes-bp folder in Positron (File → Open Folder).

nhanes-bp-checkpoint.zip is for if you fall behind. It’s the same project with a working R/01_prepare.R. You only need it if your own script isn’t working by the catch-up point.

ImportantData rule for today
  • The data are real. NHANES is a public, de-identified CDC survey. It isn’t patient data, but the NCHS data user agreement still applies: use the data for statistical analysis only, never try to identify anyone, and never link it to other data about the same people.
  • data/restricted/ is fictional. It holds one made-up file that stands in for data Claude must never read.
  • Don’t add PHI or data under a data use agreement to this project. Guardrails like deny rules are safety nets. They don’t make it OK to keep restricted data in a folder Claude Code works in. Policy comes first: follow Yale’s data classification.
  • A HIPAA-supported version of Claude is available by request (see the ITS service page for Claude Enterprise). It doesn’t approve your project, every feature, or every data set, and its features may differ. Check with ITS before using Claude Code with sensitive data.

2. What Claude sees, and who’s in control

Claude does: reads files, runs commands, and follows your project rules. You decide: what it may read and what it may change.

Claude Code sends what it reads

When Claude Code opens a file, runs a command, or reads its output, that content goes to the model. In the panel, Claude also sees text you select in the editor and the name of the file you have open. Both are on by default. Read deny rules apply to this context on a best-effort basis, so don’t rely on them to hide sensitive files.

Two patterns that keep sensitive data out:

  • Claude writes the code; you run it on restricted data elsewhere. Give Claude the data dictionary, the plan, and public or made-up rows. It writes and tests the scripts. You run the finished scripts yourself, in an approved environment that Claude never sees.
  • Public or made-up data first. Build and debug on public data, like today’s NHANES files, or on made-up data. Switch to real data only after the code is reviewed, and only where policy allows.

Read CLAUDE.md: advice

Open CLAUDE.md in the project. Claude reads it at the start of every conversation. It sets the study rules, such as:

  • data/raw/ is read-only.
  • Never read data/restricted/.
  • Write numbered scripts in R/ and save results to output/.
  • Follow docs/analysis-plan.md, and ask before deciding about missing codes, weights, or exclusions.
  • Print at most 10 rows of data.

CLAUDE.md is advice. It shapes what Claude tries to do. It doesn’t limit what Claude can do. That’s what permission rules are for.

Choose Manual mode

Click the mode indicator at the bottom of the prompt box and choose Manual. In Manual mode, Claude asks before every file edit and most shell commands. The panel may start in Auto, the built-in default in Claude Code v2.1.283 and later. It remembers the last Manual, Edit automatically, or Auto mode you picked. Check the mode indicator each time you start.

Add a deny rule: enforcement

In the panel, type / and choose Customize → Permissions. Add a Deny rule and save it to the project settings:

Permission rule 
Read(./data/restricted/**)

Or create the file .claude/settings.json in Positron’s Explorer with:

{
  "permissions": {
    "deny": ["Read(./data/restricted/**)"]
  }
}

Test the rule

Save the rule, then send:

Prompt 
This is a test of a permission rule. Use your Read tool to open
data/restricted/STANDIN_linkage_request.txt and tell me the exact
message you get. Don't try any other way to open it.

If Claude can still read the file, run /status and check the Setting sources line to confirm the project settings loaded.

Check: you want this message: File is covered by a Read deny rule in your permission settings. A polite refusal means Claude followed CLAUDE.md (advice). This message means Claude Code blocked the file (enforcement).

If Claude refuses without trying, reply: It's a test of the deny rule. Call the Read tool once on that file. If you see the text RESTRICTED-CANARY-7Q4Z, Claude read the file and the rule isn’t working. Check that the file is nhanes-bp/.claude/settings.json (the folder name starts with a dot) and that it matches the text above exactly. Then start a new conversation and test again.

WarningKnow the gap

A Read deny rule covers Claude’s own file tools and shell commands it recognizes, such as cat. It doesn’t stop a script that Claude writes and runs, such as an R script, from opening the file. So the real rule is simple: don’t put restricted data in the project.

Start version control

Ask Claude, and approve each git command when it asks:

Prompt 
Initialize a git repository here. Add a .gitignore that excludes
.claude/settings.local.json and data/restricted/. Create an empty
.here file at the top of the project. Then commit everything with
the message "Starting point".

git keeps a record of every version of your files. It’s your safety net for the rest of class.

The .here file marks the top of the project. The here package uses it to build file paths, such as here("data", "raw"), so scripts find the data wherever they run from. It’s committed with everything else, so it stays with the project.

3. Plan before you code

Claude does: reads the plan, the dictionary, and the data files, and proposes the steps. You decide: whether the plan matches the analysis you committed to.

First, you

Open data/data_dictionary.csv (not the plan yet). Look at the missing_codes, skip_logic and notes columns. Then, on paper, write down:

    1. A participant has a blank BPQ150 (“now taking BP medication”). Are they taking medication, not taking it, or unknown?
    2. BPQ020 and BPQ150 use the codes 7 and 9. What do they mean, and what should the script do with them?
    3. Should the percentages be weighted? If so, with which weight: WTINT2YR or WTMEC2YR?

Then open docs/analysis-plan.md. Did the study team decide the way you did? You’ll also check Claude’s plan against these answers.

Ask Claude for a plan

Switch to plan mode: click the mode indicator and choose Plan, or type /plan in the prompt box. In plan mode, Claude reads and proposes, and doesn’t change files. If Claude asks to run R to look at the data files, approve it. If auto mode is available in your setup, Claude may run some shell commands in plan mode without asking, and a classifier checks them. That’s expected.

Prompt 
Read docs/analysis-plan.md and data/data_dictionary.csv. Open the
codebooks in docs/codebooks/ only if you need them. Then inspect the
three files in data/raw/: variable names, types, row counts, value
counts, and ranges, printing no more than 10 rows. Propose a
step-by-step plan for R/01_prepare.R, and outline R/02_prevalence.R.
List every decision you need from me. Don't write code yet. Once I
approve, write only the first part of R/01_prepare.R: read the three
files and merge them. Then stop.

Compare, then approve

The plan opens as a document. Read it before you approve. Compare it with your notes:

If anything is wrong, add a comment to the plan or tell Claude what to change. When it’s right, approve with Yes, and manually approve edits. Don’t choose the first option, Yes, and use auto mode (or Yes, and auto-accept): it turns off the per-edit review you’ll use next.

Approving starts the work: Claude begins the first part of R/01_prepare.R at once, and each edit opens as a side-by-side diff. Review each one (see the next section).

Planning first protects research integrity: you fix the decisions before you see results.

TipReference decisions for today (open after you compare)

These come from docs/analysis-plan.md. They match the CDC definitions.

Question Today’s answer Why
Blank BPQ150 (BP medication) When BPQ020 == 2 (never told they had high BP), the medication question was skipped. Count them as not taking medication. The codebook’s skip logic. A skipped question isn’t a missing answer.
Codes 7 and 9 Missing. 7 = refused, 9 = don’t know. They’re codes, not values. Never average them.
Weights Weighted, with the exam weight WTMEC2YR, plus the strata and PSUs. Blood pressure comes from the exam. NHANES oversamples some groups, so unweighted results don’t describe U.S. adults.
Population Adults 18+, examined, at least one SBP or DBP reading, not pregnant. The plan’s question is about U.S. adults; pregnancy changes blood pressure.
Pregnancy Exclude only RIDEXPRG == 1. A missing RIDEXPRG counts as not pregnant. RIDEXPRG is recorded only for women 20–44. Everyone else is blank.
Readings Mean of the available readings 1–3. CDC’s definition.
Hypertension Mean SBP ≥ 130 or mean DBP ≥ 80 mmHg, or BPQ150 == 1 (taking BP medication). If the medication answer is missing, the readings decide. The 2017 ACC/AHA definition, as the plan states.
Age 80 Means 80 or older. Keep it; it still falls in the 60+ group. CDC top-codes age at 80 to protect privacy.
Wording Describe, don’t explain: “had hypertension,” not “caused” or “led to.” It’s a cross-sectional survey.

4. Build the prepare script

Claude does: reads the XPT files, merges them on SEQN, writes the code, runs it, and fixes errors. You decide: whether each change matches the plan.

Read and merge

Claude is now writing the first part of R/01_prepare.R. Review each diff as it appears. When Claude stops, send this prompt:

Prompt 
Check that R/01_prepare.R does only this so far, and fix it if not:
- read the three files in data/raw/ with haven::read_xpt()
- merge them on SEQN, keeping every participant in DEMO_L
- print the number of rows in each file and in the merged data
Never change anything in data/raw/. Run the script with Rscript, fix
any errors, then stop.

Check the merge: the merged data should have 11,933 rows, one for each person in DEMO_L. Only 7,801 people have blood pressure readings and 8,501 have questionnaire answers, so many rows have blanks. That’s expected.

You decide: which join did Claude use? A left join (left_join()) keeps everyone in DEMO_L. An inner join (inner_join()) keeps only the 6,615 people who are in all three files. It drops people before your population steps run, so you can’t see who left or why. If you’re not sure which one Claude used, ask it.

Finish the script

Now send this prompt so Claude writes the rest of the script:

Prompt 
Finish R/01_prepare.R. Keep the read and merge part, and make sure the
script does all of the following:
- apply the plan's population steps in order, printing n before and
  after each step
- average the available readings 1-3 for SBP and DBP
- set 7 and 9 to missing in BPQ020 and BPQ150 themselves (don't keep
  a copy with the codes)
- name the derived columns mean_sbp, mean_dbp, bp_med (1 = taking,
  0 = not), hypertension (1 = yes, 0 = no), sex, and age_group, and
  derive hypertension as the plan defines it, including the BPQ150
  skip rule
- write output/analysis_data.csv (the analysis population, with SEQN,
  the variables you used, and the derived ones) and output/prep_log.csv
  (step, n_before, n_after, reason)
Never change anything in data/raw/. Run the script with Rscript and fix
any errors.

Review each change. In Manual mode, every edit opens as a side-by-side diff. Accept or reject it, or tell Claude what to do instead. Approve the Rscript command when Claude asks. Watch the loop: write, run, read the error, fix, run again.

Check: in the diff, find two lines: the pregnancy filter (the plan says a blank RIDEXPRG counts as not pregnant: does the code keep those people?) and the line that turns 7 and 9 into missing. If you can’t find one, ask Claude to point to it.

Explain it back

You need to understand code before you trust it. Asking for an explanation is also a fast way to learn R.

Prompt 
Explain R/01_prepare.R section by section in plain language. For each
section, tell me which decision from the plan it carries out. Point
out any choice you made that I didn't ask for.

You decide: find the line that handles the blank BPQ150. Does it match your answer from the plan step? Is there a choice you didn’t ask for? If so, keep it, change it, or ask why.

5. Check it yourself

Claude does: only the git commit at the end. You decide: whether the output is right. Don’t take Claude’s summary on trust.

Open the results in Positron

In Positron’s Console, run:

library(tidyverse)
prep <- read_csv("output/analysis_data.csv")
log  <- read_csv("output/prep_log.csv")
log

Open prep from the Variables pane in the Data Explorer. If Claude renamed any columns, use its names below.

Check the numbers

Trace one person by hand

Pick participant 130559 and follow them from the raw readings to the flag:

haven::read_xpt("data/raw/BPXO_L.xpt") |>
  filter(SEQN == 130559) |>
  select(SEQN, starts_with("BPXOSY"), starts_with("BPXODI"))
haven::read_xpt("data/raw/BPQ_L.xpt") |>
  filter(SEQN == 130559) |>
  select(SEQN, BPQ020, BPQ150)
prep |> filter(SEQN == 130559)

Work out the mean SBP and mean DBP yourself. Is this person on BP medication? Do they have hypertension under the plan’s definition? Does prep agree?

TipAnswer for participant 130559

The SBP readings are 134, 129, and 129, so the mean SBP is 130.7. The DBP readings are 77, 78, and 77, so the mean DBP is 77.3. BPQ020 is 2 (never told they had high BP), so BPQ150 is blank by design: not taking medication. Only one reading is 130 or higher, but the mean is, so this person has hypertension under the plan’s definition.

Save your work with git

Prompt 
Commit R/01_prepare.R and the files in output/ with a message that
says what they do. Then show me git log --oneline.

Rewind is a partial safety net. In the panel, hover over a message and click the rewind button (check before class) to undo Claude’s file edits since then. It also undoes shell changes to files Claude had already edited. It doesn’t undo files that only a script wrote, such as everything in output/, or most edits made by subagents. git is the record.

6. Estimate, then decide what to report

Claude does: writes the survey-design code and fixes its errors. You decide: the design (already fixed in the plan), what to report, and how to say it.

NHANES isn’t a simple random sample. CDC samples in stages: in this cycle, 15 strata (groups of areas), each with 2 PSUs (primary sampling units, the first areas sampled). It also oversamples some groups. The weights make the sample represent U.S. adults. The strata and PSUs make the confidence intervals honest. CDC releases masked versions of the strata and PSUs to protect privacy. Use them exactly as given.

Predict first

Before you run anything, write down:

Write the estimate script

Prompt 
Write R/02_prevalence.R following the survey design in
docs/analysis-plan.md. Build the design on all examined participants
(WTMEC2YR > 0 in data/raw/DEMO_L.xpt), join output/analysis_data.csv
on SEQN, and then use subset() for the analysis population. Don't
filter rows before building the design. Estimate the percentage with
hypertension overall, by sex, and by age group (18-39, 40-59, 60+),
each with a Korn-Graubard 95% CI (svyciprop with method = "beta").
Also compute the unweighted overall percentage for comparison. Save
the results to output/prevalence.csv. Run the script.

A Korn–Graubard interval is a confidence interval for a percentage that works well with survey data. CDC uses it.

Review the diff. Check: find weights = ~WTMEC2YR, a subset( that comes after svydesign(, and method = "beta". If any is missing, tell Claude what the plan says. Then approve the Rscript command and open output/prevalence.csv in the Data Explorer.

You decide: what to report

Only then, open the check below.

TipCheck against CDC’s published numbers

CDC published these estimates in NCHS Data Brief 511, using the same files and the same definitions:

Group Hypertension
All adults 47.7% (95% CI 45.4–49.9)
Men 50.8%
Women 44.6%
Ages 18–39 23.4%
Ages 40–59 52.5%
Ages 60+ 71.6%

The unweighted percentage is 53.3%, higher than the weighted one. Adults 60 and older are 43.7% of the examined adults but only 30.0% of the population once weighted, and they have the most hypertension. So the weighted 47.7% is the one to report.

If you don’t match, compare the n’s first (6,084 in the analysis population), then the skip rule, the weight, and the pregnancy filter.

For the stretch goals at home: among adults with hypertension, CDC reports 59.2% aware, 51.2% treated, and 20.7% controlled. The age-adjusted overall prevalence is 44.5%.

7. Verification and research integrity

Claude is a fast collaborator that can be confidently wrong. These checks are how you find out.

Give Claude a check it can run

You decide what “correct” means. Claude writes the code that checks it. Before you send the prompt, add one rule of your own to the list.

Prompt 
Write testthat tests in tests/testthat/test-prepare.R, and a script
tests/run_checks.R that runs them. Write the checks as a function of a
data frame, so they can run on any version of the data. Test that:
- SEQN is unique
- there are 6,084 rows
- BPQ020 and BPQ150 contain no 7 or 9
- every row is an adult (18+), examined, and not pregnant
- every mean SBP lies within the range of the raw SBP readings
First show that the tests FAIL on a plain merge of the three raw files,
before any preparation. Then show that they PASS on
output/analysis_data.csv. Don't edit the tests to make them pass. Show
me the test output.

Check: read the diff of tests/ as carefully as the diff of your code. Watch for Claude editing the tests instead of the code, or “fixing” a failure by dropping rows.

Why decisions matter

NoteWhy decisions matter (open after your estimate runs)

Every row below ran without an error. Only one follows the plan.

Choice n Hypertension What happened
Per the plan (weighted, skip rule applied) 6,084 47.7% (45.4–49.9) Matches CDC.
No survey weights 6,084 53.3% Adults 60+ are over-represented in the sample (43.7% of examined adults, 30.0% once weighted), and they have the most hypertension.
Interview weight WTINT2YR instead of exam weight WTMEC2YR 6,084 48.2% Looks plausible, but blood pressure comes from the exam, so the exam weight applies.
140/90 definition instead of 130/80 6,084 32.4% A different, older definition. That’s a plan decision, not a data fix.
Medication skip left as NA in sbp >= 130 \| dbp >= 80 \| BPQ150 == 1 3,395 95.0% In R, FALSE \| NA is NA. People with normal BP and a skipped BPQ150 become NA and drop out, so mostly people with hypertension remain.
Rows with a blank BPQ150 dropped (complete case) 2,235 91.8% Drops everyone who was never told they had high BP, so mostly people with a diagnosis remain.
Pregnancy filter written as filter(RIDEXPRG != 1) 1,036 20.1% filter() drops rows where the test is NA, and RIDEXPRG is blank for everyone but women 20–44. Only young women remain.
Pregnant participants kept 6,123 47.3% Only 39 people. Not every decision moves the answer much.

One codebook skip rule nearly doubles the answer. One filter line drops five of every six people.

Read the claims

Numbers are only half the result. The sentences around them are where overclaiming creeps in. We’ll run this together on screen. You mark each sentence. If you made your own report, you can send the same prompt yourself:

Prompt 
List every sentence in reports/report.qmd that interprets a result.
For each one, give the number it relies on and the file that number
comes from. Flag any causal wording, such as "causes," "leads to," or
"effect of," and any claim the analysis plan doesn't support. Don't
change anything.

You decide: mark each sentence keep, revise, or delete. Watch for causal language, claims about groups the plan doesn’t cover, and missing caveats about who was excluded.

Human review is required

A human statistician or co-author must review the analysis before it goes anywhere. That’s required, not optional. AI review can help you prepare: /code-review reviews the current changes (if available; type / to check). But a reviewer told to find problems will always find some, and you decide which are real.

The garden of forking paths

Claude makes it cheap to try “one more” definition, weight, or subgroup. If you try many and report the one you like, your result no longer means what it says. Fix decisions in the plan before you see results, and label anything extra as exploratory. Watch for scope creep too: Claude “helpfully” changing a decision the plan already fixed.

Claude may already know CDC’s published estimate from its training. A matching number proves nothing unless it comes from your scripts. Never tune choices until the number matches.

Disclosure and the audit trail

  • Keep the record: your git log, the scripts, and .claude/settings.json. Save key conversations with /export. Note the Claude Code version and model from /status.
  • Disclose specifically, for example: “Analysis code was drafted with Claude Code (version, model). The authors reviewed all code, tested it against pre-specified checks, and reran it from the raw files.” Follow each journal’s and funder’s policy. The library’s AI guidance and resources can help.

Discuss (2 minutes): what would you need to see before you trusted an AI-assisted analysis in a paper you were reviewing?

8. Working well, and skills

Context: start fresh often

Everything Claude reads fills its context window: your messages, CLAUDE.md, every file it opens, and every line of output. As it fills, quality drops. The prompt box has a context indicator that shows how full it is.

  • New task? Start a new conversation.
  • Long session, same task? Type /compact and say what to keep, for example /compact keep the plan's decisions and the n at each step.
  • Corrected Claude twice on the same thing, and it’s still wrong? Start a new conversation with a better prompt that includes what you learned.

Model and effort

Click the model name at the bottom of the prompt box to open the picker. It lets you choose the model, and, for models that support it, the effort: how much Claude reasons on each step, from low to max. Higher effort checks more, but takes longer and uses more of your allowance. Your organization may limit the choices. If you took Getting started with Claude, these are the same two dials as the model and effort menu in the Claude app.

Skills, briefly

A skill is a saved set of instructions in a file: .claude/skills/<name>/SKILL.md. You run it by typing /<name>, or Claude loads it on its own when your request matches its description. A skill is a way to reuse a good prompt, and to share it with your team through git. If skills are enabled in the Claude app, uploads accept only these frontmatter fields: name, description, license, compatibility, metadata, allowed-tools. The example below uses disable-model-invocation, so it won’t upload there as is.

Here’s a skill that checks an NHANES file against the data dictionary:

---
name: check-data

Check $ARGUMENTS against data/data_dictionary.csv.

1. Write an R script in checks/ that reads the file (haven::read_xpt()
   for .xpt files), and run it. Report what the script prints; don't guess.
2. For each dictionary variable whose file column lists this file,
   report the number missing, the codes in its missing_codes column
   (such as 7 and 9), values outside allowed_values, and the minimum
   and maximum.
3. Report any duplicate SEQN values.
4. Print at most 10 rows of data.
5. Never edit or save over the data file. Ask me before fixing anything.
  • $ARGUMENTS is replaced by whatever you type after the skill’s name.
  • disable-model-invocation: true means Claude never starts this skill on its own. It runs only when you type /check-data.
  • Step 1 makes Claude compute the results with a script, not guess them.

9. Wrap-up

The goal, again: this class doesn’t replace learning R or statistics. You’ve seen where a coding agent speeds up good analysis, and where your expertise must stay in control.

Claude speeds this up; you decide

Stage Claude speeds this up You decide (and check)
Plan Reads the plan, the dictionary, and the codebooks; profiles the three files The question, the definitions, and the survey design, before you see results
Prepare Reads XPT files, merges on SEQN, writes the script and the n at each step Who’s in the population; whether the n flow makes sense
Recode Applies codes and skip rules to every row What a blank, a 7, a 9, or an 80 means

Claude drafts and runs. You decide and verify.

Three takeaways

  1. Protect first. CLAUDE.md is advice; a deny rule is enforcement. Choose Manual mode and start git before Claude touches the data. Claude Code sends what it reads, so keep restricted data out of the project.
  2. Plan, build, check. Plan against the analysis plan. Let Claude write and run the code. Then check the results yourself, and commit.
  3. You make the decisions. Definitions, weights, exclusions, and wording are yours. Claude speeds up the coding.

Try at home

  • Explain CDC’s own code. legacy/db511_prep_excerpt.sas is part of the SAS program CDC used for Data Brief 511. Ask Claude:

    Prompt 
    Explain legacy/db511_prep_excerpt.sas step by step for someone who
doesn't know SAS. Then translate it into R, and compare its population
rules with docs/analysis-plan.md and R/01_prepare.R. List every
difference. Don't change any existing files.

    Watch for the pregnancy-filter trap. In SAS, ridexprg ne 1 keeps people with a missing value. A word-for-word R translation, filter(RIDEXPRG != 1), drops them, and the answer falls to 20.1%. Does Claude’s translation catch it?

  • Awareness, treatment, and control. Among adults with hypertension, estimate the percentage who were aware of it (BPQ020), treated (BPQ150), and controlled (below 130/80). Plan first, then compare with Data Brief 511.

  • Age-adjust. Ask Claude how CDC age-adjusts in Data Brief 511, then add the age-adjusted overall prevalence. Check it against the brief.
