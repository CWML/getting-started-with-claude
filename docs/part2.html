Part 2: Analyzing Research Data with Claude Code

A 90-minute hands-on class for researchers with light R or Python

In this class you’ll use Claude Code inside Positron (or VS Code) to take a synthetic clinical trial from raw CSV to a Quarto report. You’ll plan first, let Claude write and run the code, check every step yourself, and finish by building a reusable tool for your own research data. Bring a laptop. This page has every prompt, ready to copy. Slides · Cheat sheet

For: faculty, postdocs, students, research coordinators, analysts, and clinicians who can read a little R or Python. Part 1 (the Claude app) is helpful but not required.

By the end of class, you’ll be able to:

  1. Configure a Claude Code project that protects raw and restricted data.
  2. Implement a plan-first workflow to clean and analyze study data.
  3. Evaluate AI-generated code and results against the analysis plan.
  4. Build a reusable command, skill, or hook for a research data task.

Before class

ImportantSetup (about 30 minutes)

Do the Part 2 setup steps before class. In short: an enterprise Claude account whose seat includes Claude Code ([how to check / who to ask]), Positron (or VS Code) with the Claude Code extension, the R or Python packages, and git with your name and email set. The Claude mobile app and the standalone CLI are optional.

TipUsing Python instead of R?

Install the Python packages listed in the setup steps instead of the R ones. In class, delete CLAUDE.md from the project, rename CLAUDE.python.md to CLAUDE.md, and start a new Claude conversation. Claude will then put scripts in python/. Every exercise below has a Python tab.

2. Data rules and project setup (0:05 – 0:17)

2a. Claude Code sends what it reads (4 min)

When Claude Code opens a file, runs a command, or sees its output, that content goes to the model. The same rules apply as for uploading a file to the Claude app. In the extension, Claude also sees text you select in the editor and the name of the file you have open.

Two patterns that keep sensitive data out:

  • “Claude writes the code, you run it on the real data.” Give Claude the data dictionary, the SAP, and a few synthetic rows. It writes and tests the pipeline. You run the finished script yourself, in an approved environment that Claude never sees.
  • “Synthetic first.” Build and debug everything on synthetic or public data, like today’s cohort. Switch to real data only after the code is reviewed, and only where policy allows.

Habits that help: keep the “print at most 10 rows” rule in CLAUDE.md. Check data in Positron’s Data Explorer rather than asking Claude to print it. Don’t open restricted files in the editor while Claude is running.

What about the HIPAA-supported version? A HIPAA-supported version of Claude is available by request: [request link]. Being HIPAA-supported doesn’t approve your project, every feature, or every data set, and Claude Code may not be covered even there. Anthropic’s documentation says the VS Code extension (the one Positron uses) isn’t covered by its HIPAA agreement, and that Remote Control and cloud sessions are turned off in the HIPAA configuration. [confirm with ITS which Claude Code surfaces are covered]. Follow [Yale data classification / policy link], and send questions to [HSIT / HIPAA Privacy Office contact]. Today’s class uses synthetic data only.

2b. CLAUDE.md and the memory hierarchy (4 min)

Open CLAUDE.md in the project. Claude reads it at the start of every conversation. It sets the study rules: data/raw/ is read-only, never read data/restricted/, write numbered scripts in R/, log every cleaning change, ask before deciding about missing data or outliers, and print at most 10 rows.

Claude Code loads instructions from several places. They’re all combined, and none overrides another:

Scope Location Shared with Use for
Managed policy Set by IT Everyone in the org Institutional rules [if your org deploys one]
User ~/.claude/CLAUDE.md Just you, every project “I prefer tidyverse and here::here()”
Project ./CLAUDE.md Your team, via git Today’s study rules
Local ./CLAUDE.local.md (gitignored) Just you, this project Personal paths and preferences
Auto memory Panel: / → Customize → Memory Just you, this machine Notes Claude saves from your corrections
  • Keep it short: the docs suggest under 200 lines per file. An import line like @docs/SAP.md loads another file every session: fine for a 2-page SAP, not for a 40-page protocol.
  • Advice, not enforcement: CLAUDE.md shapes what Claude tries to do. It doesn’t limit what Claude can do. That’s what permission rules are for (next).
  • If you took Part 1: a Claude Code project folder plays the role of your Claude app Project. The Project’s instructions become CLAUDE.md, and its files become documents in the folder, such as docs/SAP.md.
  • In the panel: / → Customize → Instructions opens your CLAUDE.md files, and Memory turns auto memory on or off and shows what it saved. In the CLI, use /memory. For your own projects, /init drafts a CLAUDE.md. If it isn’t in your panel’s / menu, run it in the CLI.

2c. Protect the data: Manual mode, a deny rule, and git (4 min)

1. Choose Manual mode. Click the mode indicator at the bottom of the prompt box and choose Manual, so Claude asks before every edit and most commands. Recent versions (v2.1.283 and later) start in Auto unless your organization turns it off. The extension ignores a project’s default-mode setting, so pick Manual yourself today.

2. Add a deny rule for data/restricted/. In the panel, type / and choose Customize → Permissions, add a Deny rule, and save it to project settings:

Read(./data/restricted/**)

Or create .claude/settings.json in Positron’s Explorer with:

{
  "permissions": {
    "deny": ["Read(./data/restricted/**)"]
  }
}

3. Test it. Start a new conversation, so the new settings are loaded, and send:

This is a test of a permission rule. Try to read
data/restricted/visit_notes.csv with your Read tool and tell me the
exact message you get. Don't try any other way to open it.

You want a permission-denied message from Claude Code, not just a polite refusal. A refusal means Claude followed CLAUDE.md (advice). A denial means Claude Code blocked the tool (enforcement).

4. Start version control. Ask Claude, and approve the commands:

Initialize a git repository here, add a .gitignore that excludes
.claude/settings.local.json and CLAUDE.local.md, and commit everything
with the message "Part 2 start".
Warning

Know the gap. Read deny rules cover Claude’s own file tools and shell commands it recognizes, such as cat and head. They don’t cover a program that opens the file itself, like an R script that Claude writes and runs. The sandbox closes that gap at the operating-system level (/sandbox; macOS, Linux, or WSL2). That’s one more reason the real rule is “don’t put restricted data in the project.”

3. Plan, build, verify (0:17 – 0:42)

Exercise 1 (hands-on, about 25 minutes). You’ll direct Claude through the SAP: plan, clean, check, analyze, report, and commit. Work at your own pace. If you fall behind, finish the cleaning script and the Data Explorer check. The instructor will show the rest on screen.

3a. Plan mode on the SAP (5 min)

Switch to plan mode: click the mode indicator and choose Plan, or type /plan in the prompt box. In plan mode, Claude reads and proposes, and doesn’t change files.

Read docs/SAP.md and data/data_dictionary.csv. Then inspect
data/raw/class_cohort.csv: column names, types, value counts, and
ranges, printing no more than 10 rows. Propose a step-by-step plan to
clean the data and run the primary analysis. List every data problem
you find, and every decision you need from me. Don't write code yet.

The prompt doesn’t name a language, because CLAUDE.md (or CLAUDE.python.md, renamed) already does.

The plan opens as a document. Read it before you approve. You can add inline comments to change anything you disagree with. When you approve, pick the option that keeps you approving each edit, not one that accepts edits automatically, so you still review every change in 3b. How many data problems did Claude find? Planning first protects research integrity: you decide the analysis before you see results.

TipWhen Claude asks how to handle a problem

CLAUDE.md tells Claude to ask you before handling missing data or outliers. For today, follow the SAP:

Claude asks about Your answer for today
Implausible values (outside the dictionary’s range) Set them to missing and log them. Don’t guess the intended value.
-99, 999, blanks, NA All are missing (see the dictionary’s missing_codes column).
Sex coded Female, Male, f, 1, 2 Recode to F/M. Assume 1 = M and 2 = F, and log it as a question for the data manager.
Duplicate rows Remove exact duplicates, then confirm that every patient_id is unique.
Mixed date formats Parse each format with its own rule, and stop if any date fails to parse.
cuff_size (not in the dictionary) Keep it, don’t use it, and log it as a question for the data manager.

Switch back to Manual. Then send:

  • Python

Print the row count before and after each step. Run it and fix any

Review each change. In Manual mode, every edit opens as a side-by-side diff. Accept or reject each change, or tell Claude what to do instead. Approve the Rscript command when Claude asks. Watch the loop: write, run, read the error, fix, rerun.

3c. Check it yourself in Positron (3 min)

Don’t take Claude’s summary on trust. In Positron’s R Console, run:

clean <- readr::read_csv("output/cohort_clean.csv")
log   <- readr::read_csv("output/cleaning_log.csv")

Python: import pandas as pd; clean = pd.read_csv("output/cohort_clean.csv")

Open clean from the Variables pane in the Data Explorer, and check:

This is what “trace every change” means: the script is the record, the log shows each change, and you’ve checked both.

3d. Table 1, the primary model, and a Quarto report (6 min)

Write R/02_table1.R (baseline characteristics by arm, as the SAP
describes) and R/03_primary_model.R (the SAP's primary analysis,
reporting n by arm and the adjusted difference with its 95% CI). Read
output/cohort_clean.csv, save results to output/, and run both.
Write reports/report.qmd, a Quarto report that presents Table 1, the
analysis population, and the primary result. Read every number from
the files in output/; don't type numbers into the text. Render it to
HTML.

Python: change the script names to python/02_table1.py and python/03_primary_model.py. The report uses Quarto’s Jupyter engine.

Open reports/report.html in Positron’s Viewer, next to its source.

Check it against the SAP. While the report renders, open R/03_primary_model.R (or python/03_primary_model.py) and R/02_table1.R next to docs/SAP.md, and check:

Anything that doesn’t match is a finding. Tell Claude what the SAP says, and have it fix the script.

TipCheck your numbers

After cleaning: 500 patients (250 per arm). Analyzed (complete case): n = 451 (Standard 222, Intensive 229). Adjusted difference, Intensive − Standard: −11.0 mmHg (95% CI −12.8 to −9.2). If yours differ, compare the n’s first. Most differences come from cleaning choices, such as how the 1/2 sex codes or implausible values were handled, and only choices that affect sbp_v0, sbp_v3, arm, site, or duplicates change the primary result.

3e. Safety nets: checkpoints, rewind, and git (3 min)

Checkpoints let you undo Claude’s file edits within a session. Hover over any of your messages and click the rewind button. Then choose Fork conversation from here, Rewind code to here, or both. Try it on a deliberate mistake:

In R/01_clean.R, rename every variable to upper case.

Accept the change, then hover over that message and choose Rewind code to here.

Checkpoints have limits. They track only edits made by Claude’s file-editing tools. Files written by your scripts (everything in output/ and reports/report.html) and changes from shell commands aren’t captured. Git is your real safety net:

Commit the scripts, the outputs, and the report with a descriptive
message. Show me git log --oneline afterward.

Break / catch-up (0:42 – 0:47)

Finish Exercise 1, or at least get R/01_clean.R working and committed. Segment 5 uses it.

4. Working well (0:47 – 0:57)

4a. Context is the budget (2 min)

Everything Claude reads fills its context window: your messages, CLAUDE.md, every file it opens, and every line of output. As it fills, quality drops. The prompt box has a context indicator that shows how full it is.

When… Do this
The session is long, but you’re on the same task /compact keep the cleaning decisions and the n at each step
You’re switching to an unrelated task Start a new conversation (new tab or New Conversation); CLI: /clear
You want to see what’s using space CLI: /context (the panel shows the indicator)
You have a quick side question /btw <question>: answered beside the chat, not added to it

Rule of thumb from the docs: if you’ve corrected Claude more than twice on the same issue, start a fresh conversation with a better prompt that includes what you learned.

4b. /model and /effort (3 min)

In the panel, click the model name at the bottom of the prompt box, or choose Switch model… from the / menu. The picker has an Effort row. In the CLI, use /model and /effort. If you took Part 1, these are the same two dials as the model and effort menu next to Send in the Claude app.

Model alias What it uses
default Your account’s default (Opus 5.5 on Enterprise, unless your admin set an organization default)
opus / sonnet / haiku Latest Opus (hardest reasoning) / Sonnet (everyday work) / Haiku (fast, simple tasks)
opusplan Opus in plan mode, then Sonnet to carry out the plan. A good fit for today’s plan-first workflow
fable / best Fable, the most capable model, for long, hard tasks (if available; may bill to usage credits)

Effort controls how much Claude reasons on each step: low, medium, high, xhigh, or max. Opus 5.5, Sonnet 5.5, and Haiku 5.5 default to medium. Higher effort tests more edge cases and verifies more, but uses more tokens and time. max applies to the current session only, and your organization may cap the levels you can choose.

ultrathink, for one turn. Put the word ultrathink anywhere in a prompt to ask for deeper reasoning on that turn only, without changing your effort setting:

ultrathink: The SAP's primary analysis is complete case, and loss to
follow-up is higher in older patients. What could that do to the
estimate, and which planned sensitivity analysis addresses it? Don't
write code.

4c. Ultracode and dynamic workflows (if enabled) (3 min)

A dynamic workflow is a script Claude writes that runs many subagents in the background. Each one checks part of the job, and you get one report at the end.

  • One task: start a prompt with the keyword ultracode. The docs say this works when you type it in the IDE extension panel. It doesn’t trigger in claude -p.
  • A whole session: /effort ultracode (CLI), or the Ultracode switch under the Effort row in the panel’s model picker. Ultracode is a setting, not an effort level. Claude then plans a workflow for every substantive task until you turn it off (/effort ultracode off).
  • Built in: /deep-research <question> searches the web from several angles, cross-checks sources, and returns a cited report. It needs web search to be available.
ultracode: review every script in R/ against docs/SAP.md, one reviewer
per script, then adversarially check each finding and report only the
ones that survive. Don't change any files.
/deep-research What do recent methods papers recommend for missing
12-month outcomes in hypertension RCTs: complete case, multiple
imputation, or mixed models?
Warning

Cost and usage. A workflow can use meaningfully more tokens than the same task in conversation, and it counts toward your plan’s usage limits. With ultracode on, every request costs more and takes longer. Try a small slice first, and turn ultracode off for routine work. Your organization can turn workflows off entirely. Verify every citation /deep-research returns, and keep study data out of research questions.

4d. Check in from your phone: /rc (if enabled) (2 min)

Remote Control lets you check on your current local session from the Claude mobile app (iOS and Android) or a browser. Start a long render or model run, then check progress or approve permission prompts from another device. If you took Part 1, this is what the phone app’s Code tab is for.

  1. In the panel, type /rc (or /remote-control). The first time, confirm Enable Remote Control. A Remote Control indicator appears in the prompt box footer. In the panel, the command takes no name and shows no QR code.
  2. On your phone, open the Claude app, tap Code, and pick the session (a computer icon with a green dot means it’s online). In a browser, the same session also shows in the Code section of the Claude web app.
  3. Type /rc again to disconnect.
  • Claude keeps running on your computer. Code execution and file access stay local, so your computer has to stay on and the session has to keep running.
  • Not the same as Claude Code on the web. Remote Control is your local session, viewed from your phone or a browser. Claude Code on the web runs separate cloud sessions on a GitHub repository (if enabled). It can’t see Positron or today’s project folder, so it isn’t a substitute for this class.
  • Governance: while connected, the session transcript (messages, responses, and tool activity) is stored on Anthropic servers. That’s another reason not to print data values into the session. It requires a claude.ai login, and on Enterprise an Owner must turn it on; custom roles also need the Remote Control permission, and your organization may require enrolled (“trusted”) devices. It isn’t available when your organization has the HIPAA configuration applied, under Zero Data Retention, through Amazon Bedrock, Google Cloud’s Agent Platform, or Microsoft Foundry, or through a custom gateway. Admins can disable it with disableRemoteControl.
  • CLI only: claude --remote-control "name" starts a session with it on, claude remote-control runs server mode with a QR code, and /mobile shows a QR code for getting the Claude app.

Optional: /fast. Fast mode makes Opus responses up to about 2.5× faster, at a higher price per token. On subscription plans it’s billed to usage credits, and on Enterprise an Owner must enable it. In the panel, use the Toggle fast mode command when your model supports it.

5. Extending Claude Code (0:57 – 1:12)

5a. Where does each instruction belong? (2 min)

Put it in… When it’s… Example in the answer key
CLAUDE.md A rule for every session “data/raw/ is read-only”
A skill you run by name A prompt you start yourself /check-data <file>
A skill Claude loads when relevant A procedure Claude should follow whenever it fits table1: journal-ready Table 1
A subagent Work in a separate context, such as an independent review biostat-reviewer
A hook Something that must happen every time Block edits to data/raw/
A deny rule Something that must never happen Read data/restricted/
  • Skills are folders with a SKILL.md file: .claude/skills/check-data/SKILL.md becomes /check-data, and text after the name fills $ARGUMENTS. Only a skill’s short description loads at first, and Claude reads the rest when your request matches. Add disable-model-invocation: true to the frontmatter, and the skill runs only when you type its name.
  • Custom commands are now skills. Claude Code merged them: an older .claude/commands/check-data.md file still works the same way, but a skill folder is the recommended form.
  • If you took Part 1: a skill you use in the Claude app is the same SKILL.md format. Skills from claude.ai can sync into Claude Code (read-only, if enabled).
  • Subagents (.claude/agents/*.md) have their own instructions and tools, and start fresh. To make one, ask Claude to create it, or write the file yourself. (The /agents command now only prints that reminder.) Hooks are scripts Claude Code runs at set points, whatever Claude decides.

5b. Demo: two skills, a reviewer, and a hook (5 min)

/check-data. This skill, which runs only when you type it, checks a file against the data dictionary by writing and running a script, so results are computed, not guessed. You’ll build it yourself in Exercise 2, so the demo runs it on redcap_export_site_A.csv.

The Table 1 skill. Claude loads this one on its own when your request matches. It encodes your judgment: no p-values for baseline characteristics in an RCT (CONSORT), missing values shown as their own row, and labels from the dictionary. A plain request should load it:

Make a baseline characteristics table by treatment arm.

The skeptical biostatistician. It has read-only tools (Read, Grep, Glob), so it can’t change files:

Use the biostat-reviewer agent to review R/01_clean.R and
R/03_primary_model.R against docs/SAP.md.

Python: review python/01_clean.py and python/03_primary_model.py.

A hook that protects data/raw/. A PreToolUse hook runs before every edit. If the target is in data/raw/, it blocks the edit and tells Claude to write to output/ instead:

Change sex from Female to F in data/raw/class_cohort.csv.

5c. Exercise 2: build one skill (8 min)

Choose A or B.

Option A (everyone): the /check-data skill. In Positron’s Explorer, create the folder .claude/skills/check-data/ and a new file in it named SKILL.md (capital letters). Paste in this text and save:

---
name: check-data
description: Data-quality check of a CSV against the data dictionary. Run it yourself with /check-data <path-to-csv>.
disable-model-invocation: true
argument-hint: [path-to-csv]
allowed-tools: Bash(git status *)
---

## Current repository state
!`git status --short`

## Task
Check the data file $ARGUMENTS against data/data_dictionary.csv.

1. Write a script in the project's language (see CLAUDE.md), saved in
   checks/, that reads the file and reports, for each variable: type
   vs. dictionary, missingness (including the codes in the dictionary's
   missing_codes column), values outside allowed_values or the plausible
   range, inconsistent category codes, and duplicate patient_id values.
2. Run it. Fix errors and rerun.
3. Summarize problems in a table: variable, issue, n affected, example
   value. Print at most 10 rows of data.
4. List variables in the file that are missing from the dictionary, and
   the reverse.
5. Don't modify the data file. Ask me before deciding how to fix anything.

Start a new conversation (or run /reload-skills), type /check-data, and run it on a REDCap export:

/check-data data/raw/redcap/redcap_export_site_B.csv

The !`git status --short` line runs before Claude sees the prompt, and allowed-tools pre-approves it. disable-model-invocation: true means Claude never starts this skill on its own; it runs only when you type /check-data. The skill says “the project’s language,” so it works unchanged for Python. (Older guides put the same text in .claude/commands/check-data.md. That still works, but skills are now the recommended form.)

Option B: a Table 1 skill. This needs output/cohort_clean.csv from Exercise 1.

Create a project skill in .claude/skills/table1/SKILL.md that builds a
journal-ready Table 1 with gtsummary from output/cohort_clean.csv,
stratified by the argument I give (default: arm). Rules: use only the
baseline variables the SAP lists, no p-values for baseline
characteristics, a separate Missing row, and labels from
data/data_dictionary.csv. Report n per group as evidence. Write a
description that makes you load it when I ask for a "Table 1" or
"baseline characteristics." Show me the file before saving.

Python: replace “with gtsummary” with “with pandas”.

Start a new conversation and test both ways: a plain request (“Make a Table 1 by site”) and /table1 site.

If it doesn’t show up, check that the file is in the right folder, then start a new conversation. If a skill doesn’t load automatically, the description is usually too vague. Put the main use case first, in the words people actually type.

Then make it yours (2 min). Change one rule so your skill fits a data task you actually do. For example, add a check your own data needs to /check-data (visit dates out of order, IDs that don’t match your study’s format), or add a rule to the Table 1 skill (your target journal’s rounding rules, or a footnote that defines each abbreviation). Save, start a new conversation, and run it again.

7. Verification and research integrity (1:20 – 1:27)

Don’t cut this segment. Claude is a fast collaborator that can be confidently wrong. These checks are how you find out.

Give Claude a check it can run

The docs’ first best practice is to give Claude a way to verify its work. Without a check, “looks done” is the only signal, and you’re the only verifier.

  • Python
Using the data dictionary and SAP, write testthat tests in

Watch for Claude editing the tests instead of the code, or “fixing” a failure by dropping rows. Read the diff of tests/ as carefully as the diff of your code.

Get an independent review: the biostat-reviewer subagent against the SAP (Segment 5), /code-review on the current diff (a bundled skill; type / to check it’s in your panel), and a human statistician or co-author, which is required, not optional.

Why cleaning matters

Same model, same data file, with and without the cleaning script:

n analyzed Intensive − Standard (mmHg) 95% CI
Raw file, no cleaning (sentinel codes read as real BP; duplicates kept) 462 −8.4 −19.6 to 2.9 (not significant)
After 01_clean 451 −11.0 −12.8 to −9.2

A few -99 and 999 codes are enough to hide a 10 mmHg treatment effect. Fast code is only as good as the checks around it.

Garden of forking paths

Claude makes it cheap to run “one more model.” If you try 20 specifications and report the one that’s significant, the p-value no longer means what it says. Pre-specify analyses in the SAP, label sensitivity and post hoc analyses as such, and use plan mode to fix decisions before you see results. Watch for scope creep too: Claude “helpfully” changing a decision the SAP already fixed.

Disclosure and the audit trail

  • Keep the record: commit .claude/ (settings, skills, agents, hooks) with the analysis. Keep settings.local.json and CLAUDE.local.md out of git. Save key sessions with /export, and note the Claude Code version and model (/status).
  • Disclose specifically, for example: “Analysis code was drafted with Claude Code (version, model). All code was reviewed by the authors, tested against pre-specified checks, and rerun from raw data.” Follow each journal’s and funder’s policy: [link to library guidance on AI disclosure].

8. Wrap-up (1:27 – 1:30)

  1. Protect first. Set up CLAUDE.md, a deny rule, Manual mode, and git before Claude touches the data. Remember: Claude Code sends what it reads.

  3. Encode your judgment once. Skills, subagents, and hooks turn good prompts into shared, versioned team tools.
