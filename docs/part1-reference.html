Quick reference: Getting started with Claude

Data rules, settings, prompts and checklists to keep after class

Last checked: 2026-10-30 against the Claude Help Center; features change often. Menu names, models and admin settings may look different in your workspace. Anything marked (if enabled) depends on your admin. Spot an error? Email justin.demayo@yale.edu.

The HIPAA-supported version of Claude

A HIPAA-supported version of Claude is available by request: [request link].

  • Being HIPAA-supported describes a contract and safeguards. It doesn’t approve your project, every feature, or every data set.
  • Before you use protected health information (PHI) there, check that: you’re in that version (not your standard account), the feature you’re using is covered, your IRB protocol and any data use agreement allow it, and you use the minimum necessary.
  • Follow [Yale data classification / policy link]. Questions go to [HSIT / HIPAA Privacy Office contact].
  • The standard Claude Enterprise account is not for PHI.
  • Features differ in the HIPAA-supported version. Some are off, and it keeps the older layout (no combined chat-and-Cowork experience). Check with [ITS] for what Yale’s version includes.

Can I share this?

The class scenarios, with full answers. “OK” still means: use the right tool, and check what comes out.

Scenario Answer Why
A published, open-access article you want explained OK Public and openly licensed. Use the open-access copy, not a library-subscription PDF.
Your own draft lecture slides OK Your own work. Take out student information, patient images and figures copied from subscription sources first.
A clinic note with the patient’s name removed No (in the standard account) Removing a name isn’t de-identification: dates, ZIP codes, record numbers and rare details can still identify someone. PHI belongs only in the HIPAA-supported version, and only if your project and data are approved for it. YNHHS notes follow YNHHS rules.
An NIH application you’re reviewing No NIH prohibits peer reviewers from using generative AI on applications (NOT-OD-23-149). The same goes for journal manuscripts you review in confidence, unless the journal says otherwise.
A YNHHS discharge-instruction template you’re revising Check first It’s YNHHS material, so YNHHS rules apply: use [Copilot] per [YNHHS AI governance]. Patient-facing text needs clinical review under YNHHS processes.
A PDF from a library subscription Check first Many library licenses don’t allow uploading to AI tools. Use the open-access version, or check [library license guidance].
Notes from a curriculum committee meeting Check first Usually fine if nothing is confidential. Look for student records, personnel matters and appeals, and take them out.

“Not here” is a valid answer

Don’t use an AI tool for:

  • Confidential peer review: grant applications and manuscripts you’ve been asked to review.
  • Final clinical decisions or doses. A clinician decides, using authoritative sources.
  • Assessed work where course policy forbids AI. Check the syllabus or ask the course director.
  • Restricted data whose data use agreement, IRB protocol or consent doesn’t allow third-party AI processing, even when de-identified. Read the agreement.
  • Personnel matters and student records unless the tool is approved for them.
  • Anything you can’t verify, such as a fact you have no way to check.
  • Tasks where checking takes longer than doing them yourself.

Licensed content

Articles, e-books and database content from library subscriptions often come with licenses that don’t allow uploading them to AI tools. Use open-access versions (for example from PubMed Central, checking the license), your own writing, or public documents. When in doubt, check [library license guidance] or ask a librarian. This is why the class uses an open-access article published under a Creative Commons license.

Incognito chats

  • Click the ghost icon in the upper right of a new chat. It isn’t available inside Projects.
  • Incognito chats aren’t saved to your history or used for memory, but they are still retained ([Yale retention period; 30 days by default]) and are included in your organization’s data exports and compliance tools.
  • In the combined chat-and-Cowork experience, incognito chats open in the previous chat layout, so Claude can’t create files or run code in them (so document skills won’t work).
  • Incognito changes what Claude remembers, not what data is allowed.

  • Example: “Write in plain language. I’m a research coordinator, not a statistician. Use short paragraphs and bullet points.”
  • Styles are being folded into skills. For tone and format, use Instructions for Claude or a skill.

Settings checklist

Projects and skills

Create a Project

Create Projects on a laptop or desktop. You can open them on your phone afterward.

  1. Projects > + New Project > give it a name (for example “Article Explainer”).
  2. Set project instructions > paste your instructions > change at least one line to fit your work.
  3. On the Project page, under Memory, turn Use account memory off (you can turn it back on later).
  4. + > add your files (knowledge).
  5. Start a new chat inside the Project and test it:
In 3 bullets: what files do you have, what will you do for me, and
what will you refuse to do?

If a file won’t upload: paste its text into the project instructions, or use the instructor’s shared Project (Can view, if sharing is enabled).

Class files: Kit A, Article Explainer (download Kit A: style guide, article copy). Kit B, Committee Assistant (download Kit B: committee pack). See the kits README for licenses.

Keep using it after class

  • Swap the article. Remove the old article file and add the next open-access paper. Keep the instructions and style guide. A text or Markdown copy works better than a PDF for finding quotes with Ctrl/Cmd+F.
  • Adapt the style guide. Edit the Audiences section for your course, clinic or newsletter. Add a rule each time you catch a mistake.
  • Kit B becomes a reusable meeting-to-minutes tool for committees that don’t handle confidential matters.
  • Share it with your team (if enabled), after checking what’s in it.
  • Big Projects: when a Project holds a lot of files, Claude searches them rather than reading everything at once, so keep asking it to quote its source.

Built-in document skills (if enabled)

  • Claude has built-in skills for Word, Excel, PowerPoint and PDF files. They need Create and edit files turned on (Settings > Capabilities) and skills enabled by your admin.
  • Claude uses a relevant skill on its own. Turn skills on or off in Customize > Skills.
  • Try it in your Kit A Project:
Using the style guide, turn the plain-language version into a
one-page Word handout.

Upload your own skill (if enabled)

  1. A skill is a folder with a SKILL.md file: a short name and description at the top, then plain-language instructions. You can add example files. Zip the folder.
  2. Customize > Skills > + > + Create skill > Upload a skill (ZIP).
  3. Your skill is private until you share it (view-only; it updates automatically when you edit it) or publish it to your organization’s library (if enabled).

Caveats:

  • Skills don’t run in incognito chats, which can’t create files or run code.
  • In the HIPAA-supported version, skills are off by default and aren’t covered by Anthropic’s agreement if turned back on [confirm with ITS].
  • Custom styles are being moved into skills (starting disabled). A migrated style may appear in the “/” menu as /name-style (check before relying on it).
  • Skills you make in the Claude app can sync into Claude Code when you sign in there with the same account (taught in Analyzing research data with Claude Code).

Model, effort and the app’s menus

Model and effort

Open the model menu next to Send.

  • Models: the current family is Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, with older models under More models. Check which appear in your menu; your admin may hide some.
  • Effort: Low, Medium, High, Extra high and Max. Each model marks its recommended level Default.
  • Thinking is always on for the current models, so effort is the main dial.
  • Fable may need usage credits on a standard seat, and is included (within limits) on premium seats [confirm Yale seat tiers].
  • Research needs an Opus model enabled for your role.

Use the smallest model and lowest effort that does the job. Bigger models, higher effort and Research use more compute: more time, more of your usage limit, and more energy. Start with the default; go smaller for simple tasks like reformatting or a glossary, and go bigger only when the answer isn’t good enough. [Dated source on AI energy use, chosen by a librarian.]

The “+” menu and the “/” menu

  • “+” in the lower left of the chat box opens a menu. Depending on what your admin has enabled, it can include: add files or photos, Memory (off for this chat), web search, Research, connectors (such as PubMed), and skills.
  • Type “/” in the chat box to open the same menu from the keyboard. What appears (skills, connectors, migrated styles as /name-style) varies by workspace, so check yours.
  • Customize > Skills and Customize > Connectors are where you manage skills and connectors (if enabled).

The phone app

The phone app is optional. Not everyone wants a work account on a personal phone; check [mobile device policy] first.

Set it up

  1. Install Claude (by Anthropic) from the App Store or Google Play.
  2. Sign in with your Yale account [sign-in steps / SSO note].
  3. Your chats, Projects, memory and skills are tied to your account, so they should appear on the phone. Opening a Project on the phone should work; create Projects on a laptop (creating one on the phone is unconfirmed — check).
  4. HIPAA-supported version: whether the phone app is available and what it may be used for is [confirm with ITS].

Talk instead of typing

  • Dictation: tap the microphone to turn speech into text, then edit before you send. Try it in your Project.

Kit A:

In two sentences, what's the main limitation of this study?

Kit B:

In two sentences, what's the most urgent action item from these notes, and who owns it?
  • Voice mode (beta): tap the sound-wave icon next to the microphone for a spoken conversation. Set the spoken language in Settings > Capabilities > Voice. It counts toward your usage limits.

Camera cautions

Anything you photograph is uploaded. Never photograph patient lists, charts, screens, whiteboards from clinical areas, badges or IDs. Public material (a conference poster, a published handout) is fine. Follow [mobile device policy].

Other things to know

  • Research on the phone (if enabled) searches only the web and silently skips connectors (if enabled) such as PubMed. Use a laptop when you need a connector.
  • The Code tab reaches Claude Code sessions. In Claude Code, /rc connects it to a Claude Code session on your laptop (if enabled; not in the HIPAA configuration). If you don’t see a Code tab, your plan or organization may not include it.

Kit A: Article Explainer

Project instructions (paste into Set project instructions, then change one line):

You help me turn research articles into accurate, plain-language
explainers for medical-school audiences.

Sources
- Use only the files in this Project unless I say otherwise. The
  article is the source of truth; the style guide sets format and tone.
- Never invent numbers or quotes. If the article doesn't say it,
  write "NOT IN ARTICLE."
- Label anything from outside the article as [general knowledge].
- Don't add references unless I ask. If I ask, mark each one
  UNVERIFIED and give its PMID or DOI so I can check it.

How to work
- Before a new explainer, ask me up to 3 questions about my audience
  and purpose, then wait for my answers.
- Report results with the actual numbers: both groups, the
  difference, and the 95% confidence interval.
- Use cautious language: "was associated with," not "caused," and
  "early evidence" for pilot or small studies.
- Flag anything that needs a clinician's or librarian's review
  before I share it.

Privacy
- I won't share patient information here. If I paste anything that
  looks like a name, MRN, date of birth, or other identifier, stop
  and remind me not to.

The privacy line is advice to Claude, not a safeguard. It’s still your job not to paste identifiers.

Turn 1: the explainer (in a new chat inside the Project)

I'm a [your role, e.g., second-year medical student / clinic nurse
educator / research coordinator / library staff].
I need an explainer of the article in this Project for
[audience, e.g., my journal club / adults in a blood-pressure clinic /
our department newsletter].

Before you write anything, ask me up to 3 questions about my audience
and purpose. Wait for my answers.

Then, following the style guide in this Project, give me:
1. Study at a glance: question, design, who was studied, where, and
   how many.
2. The main result with the actual numbers (both groups, the
   difference, 95% CI), and the main limitation the authors state.
3. A plain-language version for my audience, 150 words or fewer.
4. Three questions a careful reader should ask about the methods or
   conclusions.
5. A "Where this came from" table: for every number or claim in
   parts 1-3, the exact sentence from the article and its section,
   or [general knowledge]. If you can't find support, write
   NOT IN ARTICLE.

Rules: use only the article; don't add references; if the article
is unclear or inconsistent on something, say so.

Fast answers, if you’re stuck on Claude’s questions:

Busy readers with no stats background; goal is a 2-minute read; tone
friendly but accurate.

Turn 2: push back (critique and bias)

Now act as a skeptical reviewer of your own explainer.
- Flag any sentence that overstates the result (causal language,
  "proves," or ignoring that this was a pilot).
- Check the plain-language version against every rule in the style
  guide and tell me which rule each problem breaks.
- Check for assumptions about culture, literacy, language, gender,
  or race, for race-based clinical claims, and for who these
  results might not apply to.
- List each problem with a fix, then give me the revised
  plain-language version.

Turn 3: citation check

Suggest three other published studies on this topic a reader could
look at next. For each, give authors, year, journal, and PMID, and
mark each UNVERIFIED.

Then look up at least one PMID (see Verify and disclose). If Claude declines, that’s the behavior you want; check anything it does give you.

Tune it (switch to a smaller model or Low effort first):

Make a 6-term glossary for my audience from the article.

Build a literature search strategy

No connector needed. Refine the result with a librarian.

Help me build a PubMed search string for [topic], using MeSH terms
and keywords. Explain each block, and tell me what the search might
miss.

PubMed connector (if enabled; not covered in the HIPAA-supported version):

Search PubMed for randomized trials since 2020 on interventions to
reduce burnout in medical residents. Return a table with PMID, first
author, year, sample size, intervention, and main outcome.

Systematic or scoping review? Follow RAISE and talk to a librarian first: [library evidence synthesis service].

Patient handout, with a bias check

Write a one-page patient handout explaining what a hemoglobin A1c test
is, why it's done, and what the results mean. Write at a 6th-grade
reading level for adults with no medical background. Use short
sentences, no jargon, and end with three questions patients could ask
their clinician. Before you write, ask me any questions you need.

Then:

Now review this handout for assumptions about culture, literacy,
language, gender, or race, and for any race-based clinical claims.
List each with a fix.

Claude’s reading-level estimate is approximate: check it with a readability tool. Anything patient-facing needs clinical review before use (under YNHHS processes for YNHHS patients).

Explain a methods concept

Explain the difference between intention-to-treat and per-protocol
analysis to a first-year medical student. Use one concrete example
from a made-up drug trial. Then give me two quiz questions to check
my understanding, with answers hidden at the end.

Follow up with an iteration, for example: “Make the example about a vaccine trial instead.”

Project instructions for a course

You're helping me prepare small-group teaching materials for
second-year medical students in renal physiology.
- Match the learning objectives in the syllabus I've uploaded.
- Use plain language first, then the technical term.
- When you make a quiz question, include the answer and a one-line
  explanation of why the other options are wrong.
- Ask me before adding topics that aren't in the syllabus.

Kit A works for teaching too: set the audience to your journal club or learners.

Kit B: Committee Assistant

Project instructions:

You help me staff a curriculum committee.

Sources
- Use only the files in this Project. If the notes don't say it,
  write "NOT IN NOTES."
- Label anything not from the files [general knowledge].

How to work
- Ask me up to 3 questions before drafting, then wait for my answers.
- Refer to people by role, never by name.
- Every action item needs an owner (role), a due date, and the line
  from the notes it came from.
- Flag anything that looks confidential (personnel, student records,
  appeals) and leave it out of drafts.

Privacy
- I won't share patient information here. If I paste anything that
  looks like a name, MRN, date of birth, or other identifier, stop
  and remind me not to.

Turn 1: summary, action items and agenda

I staff the [committee name]. Before you start, ask me up to 3
questions about the audience or what has already been sent. Wait.

Then, using only the files in this Project:
1. A summary email to the committee, under 200 words.
2. An action-item table: action | owner (role) | due date | exact
   line from the notes. Use NOT IN NOTES if the notes don't say.
3. Next month's agenda that fits in 60 minutes, each item tied to
   one of the charter's duties.
4. Anything that should NOT go into a wider email, and why.
Roles only, no names; don't invent owners, dates, or decisions.

Turn 2: push back, and rewrite for the full faculty list

Now act as a careful committee chair reviewing your drafts.
- Check every action item: is the owner, due date, and quoted line
  really in the notes? Mark anything you can't trace NOT IN NOTES.
- Check the agenda against the charter's duties and the 60-minute
  limit.
- Flag anything confidential (personnel, student records, appeals)
  that slipped into a draft.
- Then rewrite the summary email for the full faculty list, leaving
  out anything that should stay within the committee.

Turn 3: check the rules and dates

When do this meeting's action items have to go out, and when is the
next meeting? For each rule you use, quote the charter line and show
your date math. If the files don't say, write NOT IN NOTES.

Then open the committee pack and check each quoted charter line yourself.

Check: trace 2 action items back to lines in the notes; confirm the confidential item was left out; check that the charter’s deadline for sending action items was applied.

Tune it (switch to a smaller model or Low effort first):

Make a 6-term glossary for a new committee member from the charter.

Make a document (if file creation and skills are enabled):

Turn next month's agenda into a one-page Word document.

Meeting notes to email and agenda

Here are rough notes from a committee meeting. Turn them into
(1) a short summary email to the committee with action items, owners,
and due dates, and (2) a draft agenda for next month's meeting.

Notes: curriculum cmte mtg. chair out, vice chair ran it. new
pharm module needs 2 more faculty reviewers by end of month - VC
asking around. student survey results late, admin coordinator
following up w/ office. debate re: moving exam week, no decision,
revisit next mtg w/ data from registrar. library offering AI
workshop, someone should forward to faculty list.

For real notes, use roles instead of names and check for anything confidential first.

For everyone: draft my AI-use disclosure

Help me write a short AI-use disclosure for [a journal article /
a grant application / a course assignment / a newsletter piece].
Here's what I did: [tool and model, dates, what I used it for, and
how I checked the output].
Draft (1) one or two sentences for the Acknowledgments or Methods,
following ICMJE guidance, and (2) a one-line version for a slide or
handout. Don't overstate or understate what the AI did, and remind
me to check the journal's or funder's own policy.

For everyone: follow-ups that work on anything

Before you start, ask me up to five questions about what I need.
Shorter. Cut the jargon. Turn the second paragraph into a bulleted list.
Now act as a skeptical reviewer. What's weak or missing?

Six prompting patterns

Pattern What it sounds like
Give context “I’m a second-year resident preparing a 10-minute teaching talk on…”
Say who it’s for “Write this for patients with no medical background, at a 6th-grade reading level.”
Show an example “Here’s an email I wrote last month. Match its tone and length.”
Ask for questions first “Before you start, ask me up to five questions about what I need.”
Iterate “Shorter. Cut the jargon. Turn the second paragraph into a bulleted list.”
Ask for critique “Now act as a skeptical reviewer. What’s weak or missing?”

Treat the first answer as a draft. Most of the value comes from the second and third turns.

What makes the Kit A Turn 1 prompt more than a basic prompt: it combines a role, a named audience, ask-first with an explicit stop, numbered output, and clear limits (a word cap, the article only, no references). The Project carries the context, so the prompt stays short and reusable. The “Where this came from” table, with NOT IN ARTICLE as an escape hatch, turns checking into a 2-minute Ctrl/Cmd+F task.

Verify and disclose

You’re responsible for what you use. Check against the source, not against Claude.

Quote check

  1. Pick 2 rows from Claude’s “Where this came from” table.
  2. Open the source (a text or Markdown copy is easiest) and press Ctrl+F (Windows) or Cmd+F (Mac).
  3. Search for 5–8 distinctive words from the quote.
  4. Mark each one: exact, paraphrased, or not there. Check that numbers match and that the section is right.
  5. Watch for numbers that don’t add up, such as counts that differ between sections. A good explainer points these out instead of smoothing them over.

Citation (PMID) check

  1. Go to pubmed.ncbi.nlm.nih.gov/<PMID> (for a DOI, doi.org/<DOI>).
  2. Does the record exist? Do the title, authors, year and journal match what Claude said?
  3. Does the abstract actually support the claim? Is there a retraction notice?
  4. If anything doesn’t match, treat the whole reference as made up. A refusal or an honest “UNVERIFIED” label is good behavior; check anyway.

Problem What it looks like
Fabrication References that don’t exist; a PMID that points to a different paper; quotes not in the source; precise numbers with no source

Bias Assumptions about culture, literacy, language, gender or race; race-based clinical claims; not saying who the results might not apply to
Agreeing too readily Claude goes along with a wrong premise. Ask it to argue the other side.

Disclose your use

  • Journals: most follow ICMJE and COPE guidance. AI tools can’t be authors. Disclose how you used them: writing help in the Acknowledgments; data collection, analysis or figures in the Methods. Check each journal’s own policy.
  • NIH peer review: NIH prohibits reviewers from using generative AI to analyze or write critiques of applications (NOT-OD-23-149, June 23, 2023).
  • NIH applications: NIH won’t consider applications that are substantially developed by AI, or that contain sections substantially developed by AI, to be the applicants’ original ideas (NOT-OD-25-132, July 17, 2025; effective for the September 25, 2025 receipt date onward).
  • Other funders: [links to other funder notices].
  • Keep a record: save key prompts and outputs, and note the date and model you used. The “Draft my AI-use disclosure” prompt in the prompt library can help.

Systematic and scoping reviews

AI use in evidence synthesis should follow the RAISE recommendations (Responsible use of AI in Evidence SynthEsis), which Cochrane, the Campbell Collaboration, JBI and the Collaboration for Environmental Evidence support in a joint position statement (2025). In short: you stay accountable, AI supports reviewers rather than replacing them, and you report its use. Claude’s Research feature is a first scan, not a systematic review. Talk to a librarian first: [library evidence synthesis service].

Cowork and Claude in Chrome

Cowork (if enabled) lets Claude carry out multi-step tasks: working with files, creating documents, and acting in a browser. Since October 23, 2026 it has been built into the Claude Enterprise chat experience, if your admin has turned it on, and tasks run in a cloud sandbox.

Claude in Chrome (if enabled) is Cowork in a side panel of your Chrome browser. It can read pages and take actions on websites. On Enterprise your admin decides whether it’s on and can limit which sites it can use.

  • Not for high-risk data. Cowork acts, not just answers: it can read, change, send and delete things.
  • Prompt injection: web pages and documents can hide instructions that try to make Claude do something you didn’t ask for. Anthropic’s own guidance advises against using Cowork with sensitive information such as healthcare portals and sensitive files.
  • HIPAA-supported version: it stays on the older layout. Cowork in the cloud is off, and Claude in Chrome isn’t covered by Anthropic’s agreement. Check with [ITS] what’s available there.
  • Safer habits: give it only public or made-up files, watch what it does, review anything before it’s sent, changed or deleted, and never point it at patient portals or electronic health records.
